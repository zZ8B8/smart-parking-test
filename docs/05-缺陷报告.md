## BUG-S1 · 计费向下取整导致少收费用

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-S1 |
| 标题 | `calc_fee()` 用向下取整计算小时数，不足 1 小时的零头被抹掉 |
| 模块 | 计费 / 出场 |
| 严重度 | 中 |
| 优先级 | P1 |
| 状态 | 待修复 |
| 关联需求 | REQ-EXIT-003、REQ-EXIT-004 |
| 关联用例 | TC-EXIT-024 ~ 026 |
| 发现方式 | 边界值分析 |
| 复现概率 | 100%（凡有零头必现） |

### 环境
MariaDB 10.4.14 · Flask 3.1 · `http://127.0.0.1:5002`

### 前置条件
使用**无月卡**的车牌（本报告用 `京A77777`），否则会被月卡免费规则掩盖。

### 复现步骤
1. 车辆入场：`POST /api/vehicles/entry`，body `{"plate":"京A77777"}`。
2. 把测试时钟前移 3660 秒（1 小时 1 分）：
   `POST /api/dev/clock`，body `{"advance":3660}`。
3. 出场结算：`POST /api/vehicles/exit`，body `{"plate":"京A77777"}`。

### 实际结果

```json
{
  "code": "OK",
  "data": {
    "id": 1, "plate": "京A77777",
    "entered_at": "2026-10-08 10:41:38",
    "exited_at":  "2026-10-08 11:42:40",
    "duration_minutes": 61,
    "fee": 5.0,
    "status": "CLOSED"
  }
}
```

停车 61 分钟，**只收了 ¥5.00**。

### 期望结果
需求写明「首小时 5 元，此后每满 1 小时 3 元（**不足 1 小时按 1 小时**）」。
「不足 1 小时按 1 小时」即小时数应**向上取整**：

| 停车时长 | 正确小时数 | 应收 | 实际小时数 | 实收 | 差额 |
| --- | --- | --- | --- | --- | --- |
| 1 小时 1 分 | 2 | ¥8.00 | 1 | ¥5.00 | **−¥3.00** |
| 2 小时 30 分 | 3 | ¥11.00 | 2 | ¥8.00 | **−¥3.00** |
| 5 小时 59 分 | 6 | ¥20.00 | 5 | ¥17.00 | **−¥3.00** |

### 影响
- **持续少收停车费**，属于直接的营收损失。
- 每次停车只要有零头就少收 3 元，在车流量大的场景下损失可观。
- 用户端显示的费用与计费标准不一致，可能引发投诉与争议。

### 根因分析
`service.py` → `calc_fee()`：

```python
def calc_fee(seconds):
    if seconds <= FREE_SECONDS:
        return 0.0
    # ⚠️ 向下取整：3660 // 3600 = 1，但按规则应是 ceil(3660/3600) = 2
    hours = int(seconds // 3600)
    if hours < 1:
        hours = 1
    fee = FIRST_HOUR_FEE + (hours - 1) * PER_HOUR_FEE
    return min(fee, DAILY_CAP)
```

用 `//`（向下取整）实现「不足 1 小时按 1 小时」，语义正好相反。

### 修复建议
改为向上取整：

```python
import math
hours = int(math.ceil(seconds / 3600.0))
if hours < 1:
    hours = 1
```

或用整数运算避免浮点误差：

```python
hours = (seconds + 3599) // 3600        # 等价于 ceil(seconds / 3600)
```

### 回归用例
`tests/bugs/test_bug_billing.py`
（3 条 xfail + 2 条对照用例：整小时计费与 15 分钟免费均正确，说明缺陷只在有零头时出现）

## BUG-S2 · 出场不幂等，重复出场会释放他人车位

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-S2 |
| 标题 | `exit_vehicle()` 不校验记录是否已出场，重复调用会重复释放车位，并可能释放他人车位 |
| 模块 | 出场 |
| 严重度 | 高 |
| 优先级 | P0 |
| 状态 | 待修复 |
| 关联需求 | REQ-EXIT-010（幂等）、REQ-EXIT-011（不得影响他人） |
| 关联用例 | TC-EXIT-027 ~ 030 |
| 发现方式 | 状态机测试 + 数据一致性反向校验 |
| 复现概率 | 100% |

### 环境
同上。

### 前置条件
车位全部空闲。

### 复现步骤
1. **车 A** 入场：`POST /api/vehicles/entry`，`{"plate":"京A77777"}` → 分到 **A-001**。
2. 时钟前移 20 分钟：`POST /api/dev/clock`，`{"advance":1200}`。
3. **车 A** 出场：`POST /api/vehicles/exit`，`{"plate":"京A77777"}` → A-001 释放。
4. **车 B** 入场：`{"plate":"京B77777"}` → 也分到 **A-001**（车位被复用是正常的）。
5. **车 A 再次出场**：`POST /api/vehicles/exit`，`{"plate":"京A77777"}` ← 异常操作。
6. 查询车位 A-001 的状态。

### 实际结果

**步骤 5** 返回 **HTTP 200**，成功：

```json
{ "code": "OK", "data": { "id": 1, "plate": "京A77777",
  "status": "CLOSED", "fee": 5.0, "...": "..." } }
```

**步骤 6** —— 车位 A-001 变成 **FREE**，而车 B 此刻**还在场**：

```
期望：OCCUPIED（plate=京B77777）
实际：FREE（plate=None）
```

**数据一致性自检同步报错**：

```json
{
  "code": "OK",
  "data": {
    "ok": false,
    "problems": [
      { "rule": "occupied_spots_equals_open_tickets",
        "detail": "占用车位 0 个，但在场记录有 1 条" }
    ]
  }
}
```

同时 `spot_logs` 里该车位出现 **2 条 EXIT 流水**（ENTRY 1 条 vs EXIT 2 条，收支失衡）。

### 期望结果
- 已出场（`CLOSED`）的记录再次调用出场接口，应返回 **400 `INVALID_STATUS`**（或等价错误码）。
- **不得**再次释放车位、不得重复写流水。
- 更关键的：释放车位前应确认「该车位当前占用的就是本次结算的这辆车」。

### 影响
- **一个车位被卖两次**：车位表显示空闲，但实际有车停着，后续车辆会被引导到已被占用的车位。
- **在场记录与车位状态不一致**，车场容量统计失真，直接影响车位调度与收入统计。
- 属于「重复提交」类问题的典型后果 —— 用户连点、网络重试、爬虫都会触发。

### 根因分析
`service.py` → `exit_vehicle()` 两处缺失：

```python
# ⚠️ 1) 取「最后一条记录」时只按 plate 排序，没有限定 status='PARKING'
ticket = db.fetch_one(
    "SELECT id, plate, spot_id, entered_at, status FROM tickets "
    "WHERE plate = %s ORDER BY id DESC LIMIT 1", (plate,))
if ticket is None:
    raise ApiError("TICKET_NOT_FOUND", ...)

# ⚠️ 2) 无条件释放车位，不检查车位当前占用的是谁
db.execute("UPDATE spots SET status='FREE', plate=NULL WHERE id = %s",
           (ticket["spot_id"],))
db.execute("INSERT INTO spot_logs (spot_id, action, ..., ) VALUES (%s,'EXIT',...)")
```

两处叠加：既能重复出场，又能释放到别人头上。

### 修复建议
1. 只取**在场**记录，并把状态判断下推到 SQL：
   ```python
   ticket = db.fetch_one(
       "SELECT id, plate, spot_id, entered_at, status FROM tickets "
       "WHERE plate = %s AND status = 'PARKING' ORDER BY id DESC LIMIT 1",
       (plate,))
   if ticket is None:
       raise ApiError("TICKET_NOT_FOUND", "未找到该车辆的在场记录", 404)
   ```
2. 用带条件的 UPDATE 保证状态流转只成功一次，并检查影响行数：
   ```sql
   UPDATE tickets SET status='CLOSED', exited_at=%s, fee=%s
   WHERE id=%s AND status='PARKING';
   -- rowcount == 0 → 说明已被结算过，直接返回 400，不再释放车位
   ```
3. 释放车位时限定车牌，避免释放到别人头上：
   ```sql
   UPDATE spots SET status='FREE', plate=NULL
   WHERE id=%s AND plate=%s;      -- 只释放「确实属于本车」的车位
   ```
4. 把「关记录 + 释放车位 + 写流水」放进**同一事务**。

### 回归用例
`tests/bugs/test_bug_exit_state.py`
（4 条 xfail + 1 条对照用例：单次正常出场完全正确）

## BUG-S3 · 并发入场超卖（一个车位发给多辆车）

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-S3 |
| 标题 | 「查空闲车位」与「占用车位」非原子，并发入场导致车位超卖 |
| 模块 | 入场 |
| 严重度 | **严重** |
| 优先级 | P0 |
| 状态 | 待修复 |
| 关联需求 | REQ-ENTRY-009 / NFR-002 |
| 关联用例 | TC-EXIT-031 ~ 033 |
| 发现方式 | 并发测试 + 数据一致性反向校验 |
| 复现概率 | 宽竞态窗口下 100%（窄窗口下偶现） |

### 环境
同上。服务以多线程模式运行（`threaded=True`）。

### 前置条件
车场 7 个车位全部空闲。

### 复现步骤
1. 准备 20 个线程，用 `threading.Barrier` 对齐起跑时刻。
2. 20 个线程同时发起：`POST /api/vehicles/entry`，各用不同车牌（`京A90000` ~ `京A90019`）。
3. 等全部返回后，统计成功数与失败码，并查询车场状态。

> 为让竞态窗口稳定可复现，把 `config.SIMULATE_DB_LATENCY` 放大到 0.3 秒
> （真实系统中这段延迟来自网络往返与线程调度）。
> 服务默认 0.05 秒时同样能复现（见 `tools/verify_bugs.py` 的实测结果）。

### 实际结果

```
车场车位总数：7
同时发起 20 个入场请求……
成功 20 笔，被拒 0 笔
占用车位 2 个，在场记录 20 条（应相等）
```

- **20 辆车全部入场成功**，但车场只有 7 个车位。
- 占用车位数与在场记录数**严重不符**（2 vs 20），多个车位被反复覆盖。
- 自检报错：`occupied_spots_equals_open_tickets` 不成立。

### 期望结果
- 无论多少并发，成功入场数 ≤ 空闲车位数（7）。
- 「占用车位数」必须始终等于「在场记录数」。
- 同一车位在同一时刻只能分配给一辆车。

### 影响
- **车位超卖**：多辆车被引导到同一个车位，现场冲突、堵车，用户体验极差。
- 车场容量统计失真，影响车位调度、收入统计与容量规划。
- 这是停车场系统在早高峰入口最典型、后果最直接的并发缺陷。

### 根因分析
`service.py` → `entry()` 把车位操作拆成了**两步无保护**的数据库交互：

```
第一步：SELECT ... FROM spots WHERE status='FREE' ORDER BY code LIMIT 1   （无锁）
        if None: 拒绝
        ─────────── 竞态窗口（一次网络往返 + 线程调度）───────────
第二步：UPDATE spots SET status='OCCUPIED', plate=? WHERE id=?
```

并发请求在第一步都读到同一个 `A-001`，于是**都通过了检查**，
到第二步各自执行占用，同一个车位被 20 辆车依次覆盖。

```python
spot = _find_free_spot(spot_type)          # 第一步：查
if spot is None:
    raise ApiError("LOT_FULL", ...)

db.simulate_round_trip()                   # 靶场把竞态窗口显式化

db.execute("UPDATE spots SET status='OCCUPIED', plate=%s WHERE id=%s", ...)  # 第二步：占
```

> **关于 `simulate_round_trip()`**：真实系统中这两步之间必然隔着一次数据库往返和
> 线程调度，那就是竞态窗口。本机数据库同机访问太快，窗口小到偶现，
> 因此靶场把这个延迟显式化（`config.SIMULATE_DB_LATENCY`），让缺陷**稳定复现**，
> 可写进回归。把该值改为 0 即可观察到窗口消失后的表现。

### 修复建议（任选其一或组合）
1. **原子条件更新**（最轻量）：
   ```sql
   UPDATE spots SET status='OCCUPIED', plate=%s
   WHERE id=%s AND status='FREE';
   -- rowcount == 0 → 说明被别人抢先占用，重新找车位或直接失败
   ```
   配一个「重试找下一个空闲车位」的循环，直到成功或确实没有空位。
2. **悲观锁**：在事务中 `SELECT ... FOR UPDATE SKIP LOCKED` 锁住一个空闲车位行，
   再占用、提交。MySQL 8 / MariaDB 10.6+ 支持 `SKIP LOCKED`，能优雅解决「抢同一个位」。
3. **乐观锁**：给 `spots` 加 `version` 字段，更新时带上版本号，失败则重试。
4. **入场排队**：对入场接口加商品级/车场级互斥锁，简单粗暴但会降低吞吐。

推荐 **方案 1 + 重试**：改动最小、无额外依赖、对现有架构友好，且天然支持高并发。

### 回归用例
`tests/bugs/test_bug_concurrent_entry.py`
（3 条 xfail + 1 条对照用例：串行入场时容量控制完全正确，
用来证明缺陷是「并发」引入的，而不是容量判断逻辑本身写错）

## BUG-S4 · 过期月卡仍然免费出场

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-S4 |
| 标题 | `_has_free_pass()` 只判断月卡是否存在，未比对有效期，过期月卡永久免费 |
| 模块 | 月卡 / 计费 |
| 严重度 | 高 |
| 优先级 | P0 |
| 状态 | 待修复 |
| 关联需求 | REQ-CARD-005、REQ-CARD-006 |
| 关联用例 | TC-EXIT-034 ~ 036 |
| 发现方式 | 业务规则测试（有效期边界） |
| 复现概率 | 100% |

### 环境
同上。

### 前置条件
初始数据含一张**已过期**月卡：`京B00001`，有效期 `2024-01-01`。

### 复现步骤
1. 确认月卡状态：`GET /api/cards/京B00001`
   → 返回 `valid_until: "2024-01-01"`，`expired: true`（**接口自己都知道它过期了**）。
2. 该车入场：`POST /api/vehicles/entry`，`{"plate":"京B00001"}`。
3. 时钟前移 3 小时：`POST /api/dev/clock`，`{"advance":10800}`。
4. 出场结算：`POST /api/vehicles/exit`，`{"plate":"京B00001"}`。

### 实际结果

```json
{
  "code": "OK",
  "data": {
    "id": 2, "plate": "京B00001",
    "entered_at": "2026-10-08 10:41:43",
    "exited_at":  "2026-10-08 13:41:43",
    "duration_minutes": 180,
    "fee": 0.0,
    "status": "CLOSED"
  }
}
```

停车 3 小时，**收费 ¥0.00**。

对照组：`京A12345`（有效期 2027-12-31，有效）停 3 小时同样 `fee = 0.0` ——
**过期月卡与有效月卡表现完全一致**，说明代码根本没看有效期。

### 期望结果
- 过期月卡应按普通车辆计费：3 小时应收 **¥11.00**（首小时 5 + 2×3）。
- 只有 `valid_until >= 当前日期` 的月卡才免费。

### 影响
- **持续漏收停车费**：车主办一次月卡就能永久免费，属于业务规则被绕过。
- 与 BUG-S1 叠加，收入损失进一步放大。
- 月卡业务失去商业意义（用户没有续费动机）。

### 根因分析
`service.py` → `_has_free_pass()`：

```python
def _has_free_pass(plate):
    card = db.fetch_one(
        "SELECT plate, valid_until FROM month_cards WHERE plate = %s", (plate,))
    if card is None:
        return False
    # ⚠️ 查出了 valid_until，却完全没用；只要记录存在就返回 True
    return True
```

值得注意的是：`get_card()` 里**已经正确算出了 `expired` 字段**（用于前端展示），
说明数据是齐的、判断逻辑也写对过，只是**计费时没有用它** —— 典型的「实现与展示不一致」。

### 修复建议
在 `_has_free_pass()` 中比对有效期：

```python
def _has_free_pass(plate):
    card = db.fetch_one(
        "SELECT plate, valid_until FROM month_cards WHERE plate = %s", (plate,))
    if card is None:
        return False
    today = _now().strftime("%Y-%m-%d")
    return card["valid_until"].strftime("%Y-%m-%d") >= today
```

或者把有效期判断直接下推到 SQL，减少出错机会：

```sql
SELECT plate FROM month_cards WHERE plate = %s AND valid_until >= CURDATE()
```

> 有效期边界建议明确约定：`valid_until = 今天` 当天是否免费？
> 本报告按「含当天」处理（`>=`）。测试用例应覆盖「到期当天」「到期次日」两个点。

### 回归用例
`tests/bugs/test_bug_card_expiry.py`
（3 条 xfail + 2 条对照用例：有效月卡免费正确、`expired` 标识计算正确）
