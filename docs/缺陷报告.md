## BUG-S1 · 计费时长向下取整，超时零头被抹掉

| 项 | 内容 |
|---|---|
| 级别 | **高** |
| 类型 | 业务规则 / 计费 |
| 模块 | 出场结算 |
| 接口 | `POST /api/vehicles/exit` |
| 定位 | `sut/service.py` → `calc_fee()` |

**复现步骤**

1. 车辆入场
2. 把系统时钟前移 61 分钟（模拟停车 61 分钟）
3. 车辆出场，读返回的 `fee`

**预期结果**：8.0 元
（规则：超过 15 分钟后首小时 5 元，此后每满 1 小时 3 元，**不足 1 小时按 1 小时**；
61 分钟 = 首小时 + 1 分钟零头，应按 2 小时计 → 5 + 3 = 8）

**实际结果**：**5.0 元**（零头被抹掉，只按 1 小时收）

```
停车 61 分钟  -> 收费 5.0 元（应为 8.0）
停车 150 分钟 -> 收费 8.0 元（应为 11.0）
```

**根因**：`calc_fee()` 用整数除法（向下取整）计算计费小时数：

```python
hours = int(seconds // 3600)      # ← 向下取整，3601 秒 → 1 小时
if hours < 1:
    hours = 1
fee = FIRST_HOUR_FEE + (hours - 1) * PER_HOUR_FEE
```

**影响**：**少收费**，且漏收集中在「超过整小时后带有零头」的绝大多数真实停车场景
（只有恰好停在整小时才正确）—— 属于直接资损，也是本系统最容易漏掉的一类缺陷。

**修复建议**：改为向上取整（不足 1 小时按 1 小时）：

```python
import math
hours = max(1, math.ceil(seconds / 3600))
```

**测试备注**：这条缺陷只有把用例设计在**边界值**上才会暴露。
按 61 / 90 / 150 分钟这类「带零头」的时长断言，才能发现；
如果只测 60 / 120 分钟这类整点，会完全漏掉。

## BUG-S2 · 重复出场会释放他人正在使用的车位

| 项 | 内容 |
|---|---|
| 级别 | **严重** |
| 类型 | 幂等性 / 数据一致性 |
| 模块 | 出场 |
| 接口 | `POST /api/vehicles/exit` |
| 定位 | `sut/service.py` → `exit_vehicle()` |

**复现步骤**

1. 车辆 A（津A12345）入场 → 出场，车位空出
2. 车辆 B（津B22222）停进刚空出的车位 → 此时占用数 = 1
3. **车辆 A 再次调用出场接口**（A 早已离场）
4. 读车位总览与在场记录

**预期结果**：第 3 步返回 400（该车已不在场），B 的车位不受影响，占用数仍为 1

**实际结果**：第 3 步返回 `HTTP 200`，**B 的车位被释放**，占用数变成 0 ——
但 B 还在场，车位状态与实际严重不符

```
第一次出场 HTTP=200，第二次出场 HTTP=200（应为 400）
B 入场后占用车位=1，A 重复出场后占用车位=0
此时仍在场车辆数=1（占用数与在场数不一致）
```

**根因**：`exit_vehicle()` 取该车牌的**最后一条记录**结算，没有校验它的状态：

```python
tickets = [t for t in store.tickets.values() if t["plate"] == plate]
if not tickets:
    raise BizError("TICKET_NOT_FOUND", "未找到该车辆的入场记录", 404)
ticket = tickets[-1]                 # ← 未校验 ticket["status"] 是否已 CLOSED
...
spot = store.spots[ticket["spot_id"]]
spot["status"] = SPOT_FREE           # ← 重复执行会释放别人正在用的车位
spot["plate"] = None
```

**影响**：
1. **车位被错误释放** → 系统认为有空位，把已被占用的车位再分配给下一辆车 → 同一车位停两辆车；
2. 已结算的记录被**重新结算**，`exited_at` 与 `fee` 被覆盖 → 账单数据不可信。

**修复建议**：
1. 结算前校验记录状态，非 `PARKING` 直接拒绝（幂等性守卫）；
2. 释放车位时校验 `spot["plate"] == plate`，避免释放他人占用的车位；
3. 数据库层面给 `(plate, status=PARKING)` 加唯一约束，从根上杜绝一车两条在场记录。

## BUG-S3 · 并发入场导致一个车位发给多辆车

| 项 | 内容 |
|---|---|
| 级别 | **严重** |
| 类型 | 并发 / 竞态条件（TOCTOU） |
| 模块 | 入场 |
| 接口 | `POST /api/vehicles/entry` |
| 定位 | `sut/service.py` → `entry()` |

**复现步骤**

1. 充电车位只有 **1 个**（C-001）
2. 12 辆车用 `threading.Barrier` 对齐后**同时**请求入场，且都指定充电车位
3. 统计成功车辆数与被分配的车位号

**预期结果**：最多 1 辆成功，其余返回 409（暂无可用车位）

**实际结果**：**11 辆入场成功，且全部被分配到同一个车位 C-001**

```
充电车位总数=1，并发车辆=12
入场成功=11 辆（应 <= 1）
被分配的车位号=['C-001']
```

**根因**：`entry()` 把「查找空闲车位」和「占用车位」写成前后两步，中间无锁：

```python
spot = _find_free_spot(spot_type)        # 第一步：12 个请求都查到同一个 C-001
if spot is None:
    raise BizError("LOT_FULL", "暂无可用车位", 409)

time.sleep(DB_ROUND_TRIP)                # 模拟两条 SQL 之间的持久层往返延迟

spot["status"] = SPOT_OCCUPIED           # 第二步：无条件占用，重复覆盖也无所谓
spot["plate"] = plate
```

由于第一步已经通过校验，后续所有请求都会成功 —— 车位「超发」。

**影响**：一个车位被分配给多辆车 → 现场实际无处可停、计费记录重复、
车位占用率统计全部失真。

**修复建议**（任一）：
1. **加锁**：对车位分配加互斥锁；
2. **原子占用**：把「找空闲车位」改成条件更新 ——
   `UPDATE spot SET status='OCCUPIED', plate=? WHERE status='FREE' LIMIT 1`，
   依据影响行数判断是否抢到（推荐）；
3. 抽号/排队机制串行化入场请求。

**测试备注**：成功车辆数受线程调度影响会有浮动（每次 11~12 辆），
但**「所有成功的车都被分配到同一车位」是稳定复现的**，这也是更本质的现象。

## BUG-S4 · 过期月卡依然免费出场

| 项 | 内容 |
|---|---|
| 级别 | **高** |
| 类型 | 业务规则 / 时效性 |
| 模块 | 月卡 / 计费 |
| 接口 | `POST /api/vehicles/exit`、`POST /api/cards` |
| 定位 | `sut/service.py` → `_has_free_pass()` |

**复现步骤**

1. 给车牌办理月卡，有效期填 **2020-01-01**（早已过期）
2. 该车入场，时钟前移 3 小时
3. 出场，读 `fee`

**预期结果**：11.0 元（月卡已过期，应按正常标准收费）

**实际结果**：**0.0 元**

```
月卡有效期=2020-01-01（已过期），停车 3 小时
实际收费 0.0 元（应为 11.0）
```

**根因**：`_has_free_pass()` 只判断月卡是否存在，完全没有比对 `valid_until`：

```python
def _has_free_pass(plate):
    card = store.cards.get(plate)
    if card is None:
        return False
    # 只判断月卡是否存在，没有比对有效期 —— 过期月卡依然免费。
    return True
```

**影响**：**持续少收费**。过期用户只要不续费，就能永久免费停车；
且不会出现在任何「异常」报表里（系统认为一切正常），是典型的静默资损。

**修复建议**：与当前日期比较后再放行：

```python
from datetime import date
return card["valid_until"] >= date.today().isoformat()
```

并补充「月卡到期前提醒续费」「到期当天是否仍可免费」等业务规则的明确定义与判定用例。

**测试备注**：这条缺陷用「有效期内免费」这一条用例**测不出来**——
必须补一条**反向用例**（过期卡应收费）。
这也是等价类设计中「多因素组合」的价值：月卡 × 有效期 = 2 个维度，
只测一个维度会漏掉一半风险。

## 两个类别的思考

四条缺陷可以归成两类，暴露的测试设计要点完全不同：

| 类别 | 缺陷 | 怎样才能发现 |
|---|---|---|
| **规则类**（S1 / S4） | 计费零头、月卡时效 | 用例必须踩在**边界**和**反向组合**上：61 分钟、过期卡 |
| **状态类**（S2 / S3） | 重复出场、并发入场 | 必须**重复调用**或**并发调用**同一接口，单次顺序调用永远测不出来 |

结论：只做「正常路径 + 明显异常路径」的功能测试，这四条一条都抓不到。
