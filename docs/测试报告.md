**如何解读 11 条「期望失败」**：
这些用例断言的是「正确系统应有的行为」（如「61 分钟应按 2 小时计费」）。
当前系统确实不满足，所以它们失败 —— 失败即证明缺陷被真实抓到。
用 `xfail` 标记的好处：**一旦缺陷被修复，用例会自动变成 `XPASS` 提醒回归**。

## 5. 测试结论

| 维度 | 评价 |
|---|---|
| 基本功能 | **通过**。车位分配、入场校验、出场释放、记录查询均正常 |
| 计费正确性 | **不通过**。带零头的时长一律少收费（BUG-S1） |
| 数据一致性 | **不通过**。重复出场会释放他人车位、覆盖已结算费用（BUG-S2）；并发入场一车位多车（BUG-S3） |
| 月卡规则 | **不通过**。有效期未校验，过期后永久免费（BUG-S4） |

**总体**：主流程可用，但**不具备上线条件** ——
4 条缺陷全部指向**实际资损**（少收费、重复计费、月卡白停）或**资源错配**（车位超发），
且都不会抛出异常、不会进错误日志，属于最难发现的静默缺陷。

建议修复优先级：**BUG-S3 → BUG-S2 → BUG-S1 → BUG-S4**。

## 6. 修复后的验证方式

修复代码后重新跑测试：

```bash
pytest tests/bugs -v
```

输出从 `xfail` 变成 **`xpass` / `passed`**，说明缺陷已修复且未引入回归。
`xfail` 用例在这里起到**回归守护**的作用。

## 8. 测试设计经验小结

本项目 4 条缺陷，**没有一条能被「正常路径 + 明显异常路径」的功能测试抓到**：

| 缺陷 | 为什么常规用例抓不到 | 需要什么用例 |
|---|---|---|
| BUG-S1 | 60 / 120 分钟这些整点时长都算对 | **边界值**：61 / 90 / 150 分钟这种带零头的时长 |
| BUG-S2 | 单次顺序调用出场完全正确 | **重复调用**：同一接口再调一次 |
| BUG-S3 | 单线程串行入场完全正确 | **并发调用**：多线程同时打同一接口 |
| BUG-S4 | 「有效期内免费」这条用例会通过 | **反向用例**：过期卡应收费（多因素交叉） |

一句话：**功能测试保证「做对了能过」，边界 / 重复 / 并发 / 反向用例才能发现「错了也能过」。**
